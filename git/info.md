# 1. Основные принципы работы Git

**1. Снимки (Snapshots), а не различия:**
- Git хранит снимки состояния файлов, а не различия между версиями
- При коммите Git сохраняет ссылку на снимок всех файлов
- Неизмененные файлы хранятся как ссылки на предыдущий снимок

**2. Локальность операций:**
- Большинство операций выполняются локально
- Не требуется доступ к серверу для работы с историей
- Быстрые операции благодаря локальной базе данных

**3. Целостность данных:**
- Все объекты в Git идентифицируются SHA-1 хешем
- Невозможно изменить содержимое без изменения хеша
- Гарантирует целостность данных

**4. Три состояния файлов:**
- **Modified (изменен):** файл изменен, но не добавлен в staging
- **Staged (подготовлен):** файл отмечен для включения в следующий коммит
- **Committed (закоммичен):** файл сохранен в локальной базе данных

**5. Три области (areas):**
- **Working Directory (рабочая директория):** файлы, с которыми вы работаете
- **Staging Area (индекс):** подготовленные к коммиту изменения
- **Git Directory (репозиторий):** база данных с историей коммитов

# 2. Архитектура Git

**Объекты Git:**

**1. Blob (Binary Large Object):**
- Хранит содержимое файла
- Идентифицируется SHA-1 хешем содержимого

**2. Tree (дерево):**
- Представляет структуру директорий
- Содержит ссылки на blobs и другие trees
- Хранит имена файлов и права доступа

**3. Commit (коммит):**
- Снимок состояния проекта в определенный момент
- Содержит: ссылку на tree, ссылки на родительские коммиты, автора, дату, сообщение

**4. Tag (тег):**
- Постоянная ссылка на конкретный коммит
- Используется для отметки релизов

**Структура репозитория:**
```
.git/
├── HEAD              # Указатель на текущую ветку
├── config            # Конфигурация репозитория
├── objects/          # База данных объектов (blobs, trees, commits)
├── refs/             # Ссылки на коммиты (ветки, теги)
│   ├── heads/        # Ветки
│   └── tags/         # Теги
└── index             # Staging area
```

# 3. Branch Strategy

## 3.1. Что такое ветка (Branch)?

**Ветка** - это подвижный указатель на коммит. Ветки позволяют работать над разными версиями проекта параллельно.

**Зачем нужны ветки:**
- Изоляция разработки новых функций
- Параллельная работа нескольких разработчиков
- Экспериментирование без риска для основного кода
- Поддержка нескольких версий продукта

**Как работают ветки:**
- Ветка - это просто указатель на коммит
- HEAD - указатель на текущую ветку
- При создании коммита ветка автоматически перемещается вперед

### 3.2. Основные концепции ветвления

**Main/Master ветка:**
- Основная ветка проекта
- Содержит стабильный, рабочий код
- Обычно защищена от прямых коммитов

**Feature ветки:**
- Временные ветки для разработки новых функций
- Создаются от main, сливаются обратно после завершения
- Название: `feature/название-функции`

**Release ветки:**
- Ветки для подготовки релиза
- Используются для финальных исправлений перед релизом
- Название: `release/версия`

**Hotfix ветки:**
- Ветки для срочных исправлений в продакшене
- Создаются от main, сливаются в main и develop
- Название: `hotfix/описание`

**Develop ветка:**
- Ветка разработки
- Содержит последние изменения для следующего релиза
- Интеграционная ветка для feature веток

### 3.3. Типы стратегий ветвления

**1. Trunk-based Development:**
- Минимальное ветвление
- Все работают в одной ветке (trunk/main)
- Короткоживущие feature ветки (1-2 дня)
- Требует частых коммитов и хорошего CI/CD

**2. Feature Branch Workflow:**
- Каждая функция в отдельной ветке
- Ветки создаются от main и сливаются обратно
- Простая модель для небольших команд

**3. Git Flow:**
- Строгая модель с несколькими типами веток
- Разделение на main, develop, feature, release, hotfix
- Подходит для проектов с регулярными релизами

**4. GitHub Flow:**
- Упрощенная версия Git Flow
- Только main и feature ветки
- Подходит для непрерывного развертывания


**5. GitLab Flow:**
- Комбинация Git Flow и GitHub Flow
- Использует environment branches (staging, production)
- Интеграция с GitLab CI/CD
