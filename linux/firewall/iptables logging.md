## Зачем логировать в iptables

- **Отладка:** понять, какие пакеты доходят до фаервола и почему блокируются.
- **Безопасность:** фиксировать подозрительные попытки доступа (скан портов, попытки на SSH).
- **Аудит:** кто и откуда подключался к сервисам.

**Важно:** target **LOG** не решает судьбу пакета - он только пишет в ядро (kernel log), после чего проверка правил продолжается. Поэтому правило с `-j LOG` обычно ставят **перед** правилом с `-j DROP` или `-j REJECT`, а следующее правило уже отбрасывает пакет.

## Базовое правило с LOG

```bash
# Логировать все входящие пакеты, которые потом будут отброшены (ставьте перед DROP/REJECT)
sudo iptables -A INPUT -p tcp --dport 22 -j LOG --log-prefix "IPTables-SSH: " --log-level 4
```

Параметры:
- **--log-prefix "строка"** - префикс в каждой записи (удобно фильтровать в syslog). Рекомендуется короткий уникальный префикс.
- **--log-level 4** - уровень syslog (4 = warning). По умолчанию используется уровень из ядра; 4 обычно попадает в стандартные логи.

После срабатывания запись попадёт в **kernel log**. Смотреть можно так:

```bash
# Просмотр логов ядра (последние записи)
sudo dmesg | tail -50

# Или через journalctl (systemd)
sudo journalctl -k | tail -50

# Только сообщения с префиксом
sudo dmesg | grep "IPTables-SSH"
sudo journalctl -k -g "IPTables-SSH"
```

## Типичная схема: LOG перед DROP

Чтобы логировать **только отбрасываемый** трафик, добавьте правило с LOG **выше** правила DROP, с теми же условиями (или шире). Тогда сначала пишется лог, затем пакет отбрасывается следующим правилом.

Пример: логировать все входящие TCP-пакеты на порт 22, которые не попали под разрешающие правила и будут отброшены политикой по умолчанию. Упрощённо - правило «логировать попытки на SSH» перед общим DROP:

```bash
# Сначала разрешающие правила (lo, ESTABLISHED,RELATED, свой SSH с доверенной сети и т.д.)
# ...

# Логировать входящие на порт 22 (SSH), затем отклонить
sudo iptables -A INPUT -p tcp --dport 22 -j LOG --log-prefix "IPTables-SSH-DROP: " --log-level 4
sudo iptables -A INPUT -p tcp --dport 22 -j REJECT --reject-with tcp-reset

# Или логировать всё, что дойдёт до конца цепочки (перед политикой DROP не получится, но можно логировать «подозрительное»)
# Например: логировать все попытки на порт 3306 (MySQL), затем DROP
sudo iptables -A INPUT -p tcp --dport 3306 -j LOG --log-prefix "IPTables-MySQL: "
sudo iptables -A INPUT -p tcp --dport 3306 -j DROP
```

Порядок: **LOG → DROP/REJECT**. Один и тот же пакет не должен попадать в два правила LOG подряд без необходимости, иначе дубли в логах.

## Ограничение частоты логирования (rate limit)

Слишком много срабатываний (например, сканирование портов) может забить лог и диск. Можно ограничить частоту записей модулем **limit**:

```bash
# Логировать не чаще 3 раз в минуту (в среднем 1 раз в 20 секунд)
sudo iptables -A INPUT -p tcp --dport 22 -j LOG --log-prefix "IPTables-SSH: " -m limit --limit 3/min --limit-burst 5
sudo iptables -A INPUT -p tcp --dport 22 -j REJECT --reject-with tcp-reset
```

- **--limit 3/min** - средняя частота записей.
- **--limit-burst 5** - разрешить короткий «всплеск» из нескольких записей, после чего следовать лимиту.

Так вы сохраняете возможность видеть атаки, но не переполняете логи.

## Куда пишутся логи

- Записи **LOG** попадают в подсистему логирования ядра (netfilter).
- В большинстве дистрибутивов их перехватывает **rsyslog** или **systemd-journald** и они оказываются в:
  - **/var/log/syslog** (Debian/Ubuntu, при настройке по умолчанию),
  - **/var/log/messages** (часть дистрибутивов),
  - **journalctl -k** (journal, kernel messages).

Чтобы перенаправить только iptables LOG в отдельный файл, настраивают правила в **rsyslog** (например, по `--log-prefix`). Пример для rsyslog:

```text
# /etc/rsyslog.d/iptables.conf
:msg, startswith, "IPTables-" -/var/log/iptables.log
& stop
```

После изменений перезапустите rsyslog. Тогда записи с префиксом `IPTables-` будут попадать в `/var/log/iptables.log`.

## Практические советы

1. **Префикс** - короткий и уникальный (`IPTables-SSH`, `FW-DROP`), чтобы удобно искать в логах.
2. **Не логировать всё подряд** - только нужные цепочки/порты, и по возможности с **limit**, чтобы не переполнять диск.
3. **Ротация логов** - для `/var/log/iptables.log` настройте logrotate (или используйте стандартную ротацию syslog).
4. **Порядок правил:** разрешающие → логирующие (опционально) → запрещающие (DROP/REJECT).

После настройки проверьте: выполните действие, которое должно быть залогировано (например, попытку подключения на закрытый порт), затем проверьте `dmesg` или `/var/log/syslog` / `journalctl -k` по вашему префиксу.
