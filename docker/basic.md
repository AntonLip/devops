# Linux, namespaces и контейнер без Docker

Контейнер в продакшене чаще всего запускают через **Docker** или **Kubernetes**, но с точки зрения ядра Linux это не «магия образа», а **изолированные процессы** с ограничениями. Понимание **namespaces**, **cgroups** и слоя безопасности помогает отлаживать сеть, volume’ы и лимиты ресурсов без догадок. В этом файле - опора на механизмы ядра и минимальный пример изоляции **без** Docker.

---

## 1. Зачем DevOps знать устройство контейнера

- **Сеть:** почему контейнер «видит» свой `eth0`, как устроен NAT и проброс портов - это следствие **network namespace**.
- **Файловая система:** bind mount и образы опираются на **mount namespace** и слои.
- **Ресурсы:** лимиты CPU/RAM в Docker/Kubernetes мапятся на **cgroups**.
- **Безопасность:** «root в контейнере» ≠ безопасно по умолчанию - играют **capabilities**, **seccomp**, **AppArmor/SELinux**.

Без этого языка сложно читать инциденты и документацию по runtime’ам.

---

## 2. Контейнер с точки зрения ядра: не «мини-ВМ»

| | Виртуальная машина | Linux-контейнер |
|---|---|---|
| Изоляция | Отдельное «железо» через гипервизор (KVM, Xen…) | Общее ядро хоста, изоляция **пространств имён** и **политик** |
| Оверхед | Выше (эмуляция/виртуализация устройств) | Ниже (нет отдельного ядра гостя) |
| ОС | Своя гостевая ОС | Тот же тип ядра, другой rootfs и окружение процесса |

Контейнер - это **группа процессов** в ограниченном окружении, а не полноценная виртуальная машина.

## 3. Namespaces: одна система - несколько «вселенных»

**Namespace** (пространство имён) в ядре Linux - это механизм **виртуализации представления** о ресурсе. Процессы на одной машине делят **одно ядро и одно железо**, но часть глобальных таблиц ядра (процессы, сеть, монтирования…) для них **размножена**: у каждого namespace свой срез данных.

Интуиция: это не копирование файлов на диске, а **отдельный контекст в памяти ядра**. Два процесса в разных pid namespace могут одновременно иметь «процесс с PID 1» - в своих таблицах; два net namespace имеют независимые интерфейсы и стеки TCP/IP.

### 3.1. Зачем это контейнеру

| Namespace | Что изолируется | Типичный эффект, который вы заметите |
|-----------|-----------------|----------------------------------------|
| **mnt** (mount) | Список точек монтирования | Свой «корень» и свои bind mount’ы без влияния на хост |
| **uts** | Имя хоста и NIS-домен (`uname`) | Свой `hostname` внутри контейнера |
| **ipc** | SysV IPC, очереди сообщений | Процессы не видят семафоры хоста и наоборот |
| **pid** | Нумерация процессов | Внутри своего дерева снова есть PID 1 |
| **net** | Сетевой стек | Свои интерфейсы, маршруты, правила firewall в этом namespace |
| **user** | UID/GID и capability в пользовательском ключе | Root внутри может быть обычным пользователем снаружи (rootless) |
| **cgroup** | Видимость иерархии cgroup | Ограничение того, что процесс «видит» про cgroups (актуально для nested-сценариев) |

Docker и OCI runtime при старте контейнера создают **набор** namespace’ов и запускают в нём процесс; вы ниже делаете то же по частям вручную.

### 3.2. Пример 1: UTS namespace - «другой hostname» без смены имени всей машины

**Смысл:** глобальное имя хоста в Linux хранится в контексте **uts namespace**. Новый uts namespace = можно вызвать `hostname` и изменить имя **только для процессов внутри**.

**На хосте** (откройте второй терминал и не закрывайте):

```bash
hostname
```

**В первом терминале** создайте новый uts namespace и оболочку внутри:

```bash
sudo unshare --uts /bin/bash
```

**Внутри** (приглашение оболочки после команды):

```bash
hostname demo-container
hostname
```

Вы увидите `demo-container`. Во **втором** терминале на хосте `hostname` по-прежнему покажет старое имя: изменение не «пробило» всю систему, потому что uts namespace **разделил** контекст имён.

Выйти из оболочки: `exit`.

### 3.3. Пример 2: network namespace - «свой сетевой мир»

**Смысл:** в новом **net** namespace сетевой стек пустой: обычно только **loopback**, нет вашего реального `eth0`/`wlan0` в том виде, как на хосте.

```bash
sudo unshare --net /bin/bash
```

Внутри:

```bash
ip link
ip route
```

Сравните с выводом тех же команд **на хосте** в другом терминале: набор интерфейсов и маршрутов разный. Чтобы из такого namespace ходить в интернет, как в Docker, добавляют **veth** + мост/NAT на хосте; здесь важна **идея изоляции**, а не полная схема с NAT.

`exit` для выхода.

### 3.4. Пример 3: PID namespace + правильный `/proc` - «своё дерево процессов»

**Смысл:** в новом **pid** namespace процесс видит **только** процессы своего поддерева; первый процесс в namespace становится **PID 1** в этой «вселенной». Чтобы команды вроде `ps` показывали осмысленную картину, нужно смонтировать **proc** в этом контексте: флаг **`--mount-proc`** у `unshare` как раз создаёт mount namespace и монтирует `procfs`, привязанный к новому pid namespace.

```bash
sudo unshare --fork --pid --mount-proc /bin/bash
```

Внутри:

```bash
echo "Мой PID внутри namespace: $$"
ps aux
```

Вы увидите **короткий** список процессов (часто только оболочка и то, что вы запустите), а первый процесс в этом namespace ведёт себя как **init** для данного дерева. На хосте в `ps aux` по-прежнему полная картина - другой pid namespace.

`exit` для выхода.

### 3.5. Пример 4: mount namespace (идея)

**Смысл:** список «что смонтировано куда» разный для разных **mnt** namespace - поэтому контейнер может иметь `/` из образа, не ломая корень хоста. Полноценный пример с отдельным rootfs - через `chroot` или overlay; для первого знакомства достаточно связки **mnt + pid** в Docker, реализованной runtime’ом. Ручной `chroot` в отдельный rootfs (Alpine tarball и т.д.) - логичное продолжение, но требует подготовленного каталога; см. опциональный шаг в разделе 6.

### 3.6. Как это читать вместе

- **Namespaces** отвечают на вопрос: *что процесс **видит*** (процессы, сеть, hostname, монтирования).
- Они **не** сами по себе ограничивают CPU/RAM - для этого нужны **cgroups** (раздел 4).

## 4. cgroups: учёт и лимиты ресурсов

**cgroups** (control groups) - механизм ядра для **группировки процессов** и применения к группе **лимитов и учёта**: память, CPU, I/O, число процессов и т.д.

- **Учёт:** сколько реально потреблено CPU/памяти группой - основа для метрик и fair share.
- **Лимиты:** «не больше 512 МиБ RAM», «не больше 50% одного CPU» - то, что в Kubernetes задают как `limits`, а в Docker - как `--memory`, `--cpus`.

### 4.1. Версии: v1 и v2

На современных дистрибутивах часто **cgroup v2** (единая иерархия, файлы вроде `memory.max`, `cpu.max` в каталоге группы). Старый **v1** имел отдельные деревья `memory`, `cpu`… Проверка:

```bash
mount | grep cgroup
```

Если видно `cgroup2` на `/sys/fs/cgroup`, ниже ориентируемся на **v2**. Если у вас v1, смысл тот же (лимиты через файлы контроллеров), но пути другие - смотрите документацию дистрибутива.

### 4.2. Пример: лимит памяти для группы процессов (cgroup v2)

Идея: создать **дочернюю cgroup**, записать лимит в `memory.max`, поместить процесс в группу через `cgroup.procs`.

**Внимание:** на системах с жёстким управлением cgroups со стороны **systemd** прямое создание каталога под `/sys/fs/cgroup` иногда ограничено или сбрасывается. Тогда используйте вариант из п. 4.3. Для учебной VM или пользовательского cgroup-окружения часто работает так:

```bash
sudo mkdir -p /sys/fs/cgroup/devops-demo-mem
echo 100M | sudo tee /sys/fs/cgroup/devops-demo-mem/memory.max
```

Если файла `memory.max` нет или команда на запись в `cgroup.subtree_control` родителя не проходит, перейдите к **systemd-run** (п. 4.3).

Поместить **текущую** оболочку в группу (оболочка начнёт считаться частью этой cgroup; дочерние процессы наследуют):

```bash
echo $$ | sudo tee /sys/fs/cgroup/devops-demo-mem/cgroup.procs
```

Запустите что-то тяжёлое по памяти в этой же сессии - при превышении лимита ядро применит **OOM** к процессам группы (поведение описано в документации memory controller).

Снять процесс с лимита (переместить обратно в корень v2), очистка после эксперимента:

```bash
echo $$ | sudo tee /sys/fs/cgroup/cgroup.procs
sudo rmdir /sys/fs/cgroup/devops-demo-mem
```

(Если `rmdir` не удаляется - в группе ещё есть процессы; переместите их или завершите.)

### 4.3. Альтернатива: transient unit и лимиты без ручных путей

Удобный способ на хостах с systemd - **временная** cgroup с параметрами:

```bash
systemd-run --scope -p MemoryMax=100M -p CPUQuota=50% /bin/bash
```

Внутри запущенной сессии действуют лимиты; это тот же механизм cgroup «под капотом», но без ручного `mkdir`.

### 4.4. Связка с Kubernetes и Docker

- **`docker run --memory 512m`** → запись в соответствующие поля cgroup для контейнера.
- **`resources.limits.memory` в Pod** → kubelet настраивает cgroup для pod/containerd.

Namespaces **не заменяют** cgroups: первые режут **видимость и изоляцию контекста**, вторые - **справедливость и потолки по ресурсам**.

---

## 5. Дополнительный слой: capabilities, seccomp, LSM

Namespaces и cgroups - основа «контейнерности» на ядре. Поверх часто включают:

- **Capabilities** - нарезка привилегий root (например, только `NET_BIND_SERVICE`).
- **seccomp** - белый/чёрный список системных вызовов.
- **AppArmor / SELinux** - мандатные профили доступа к файлам и сокетам.

Образ и флаги запуска в Docker могут ослаблять или ужесточать этот слой; углублённо - в темах безопасности контейнеров.

## 6. Сквозная последовательность: изолированный процесс средствами ядра

Ниже три **логических блока** - их лучше выполнять по порядку в отдельных сессиях, чтобы не смешивать эффекты:
1. **Только namespaces** - меняется «картина мира» для процесса (hostname, сеть, PID, `/proc`), **без** лимита памяти.
2. **Только cgroup** - лимит памяти для **текущей** оболочки на хосте, **без** новых namespace.
3. **Namespaces + cgroup** - сначала создаётся cgroup и лимит, затем запускается `unshare`, и **внутри** новой оболочки процесс **присоединяют** к cgroup (так лимит действует на изолированное дерево процессов).

Почему нельзя в произвольном порядке «сначала поместить в cgroup, потом unshare» без уточнения: `unshare` порождает **новый** процесс; запись **`cgroup.procs` до** `unshare` относится к старой оболочке, а не к оболочке внутри namespace. Поэтому в блоке 3 лимит подключается **сразу после** входа в `unshare`.

**Условия:** Linux, `sudo`, пакет **util-linux** (`unshare`). Эксперименты - на тестовой машине или VM.

### 6.1. Эталон «как на хосте»

В **отдельном** терминале ничего не меняйте - только смотрите:

```bash
hostname
ip link | head
ps -e | wc -l
```

Это эталон для сравнения с тем, что увидите внутри изоляции.

### 6.2. Блок A - только namespaces (UTS + net + PID + proc)

Одна команда создаёт новые **uts**, **net**, **pid** и монтирует **proc** в согласованном с pid namespace виде (`--fork` нужен, чтобы процесс в новом pid namespace не оставался «лишним» в старом дереве):

```bash
sudo unshare --uts --net --fork --pid --mount-proc /bin/bash
```

**Внутри** выполните по шагам и читайте вывод:

```bash
hostname
hostname isolated-demo
hostname
ip link
ip route
ps aux
echo "PID этой оболочки внутри namespace: $$"
```

Во **втором** терминале на хосте снова выполните `hostname` и `ps -e | wc -l`: имя хоста и число процессов **не обязаны** совпадать с тем, что внутри - вы в другом **uts** и **pid** namespace; сеть - в отдельном **net** namespace.

Завершите изолированную сессию:

```bash
exit
```

### 6.3. Блок B - только cgroup v2 (лимит памяти, без `unshare`)

Проверьте, что в каталоге группы появляется `memory.max` (если нет - используйте вариант **systemd-run** из п. 4.3 выше):

```bash
sudo mkdir -p /sys/fs/cgroup/devops-lab-only-cg
echo 100M | sudo tee /sys/fs/cgroup/devops-lab-only-cg/memory.max
echo $$ | sudo tee /sys/fs/cgroup/devops-lab-only-cg/cgroup.procs
```

Текущая оболочка и все дочерние процессы наследуют эту cgroup. Для проверки учёта можно открыть:

```bash
cat /sys/fs/cgroup/devops-lab-only-cg/memory.current
```

Снять оболочку с лимита и удалить группу (пока в ней нет процессов):

```bash
echo $$ | sudo tee /sys/fs/cgroup/cgroup.procs
sudo rmdir /sys/fs/cgroup/devops-lab-only-cg
```

### 6.4. Блок C - namespaces и cgroup вместе

Создайте отдельную группу (имя другое, чтобы не пересечься с блоком B):

```bash
sudo mkdir -p /sys/fs/cgroup/devops-lab-combo
echo 200M | sudo tee /sys/fs/cgroup/devops-lab-combo/memory.max
```

Запустите изоляцию namespace (как в блоке A):

```bash
sudo unshare --uts --net --fork --pid --mount-proc /bin/bash
```

**Сразу во вновь открывшейся оболочке** присоедините **её** PID к cgroup (именно этот PID - корень нового дерева в pid namespace):

```bash
echo $$ | sudo tee /sys/fs/cgroup/devops-lab-combo/cgroup.procs
```

Проверьте, что PID попал в группу:

```bash
cat /sys/fs/cgroup/devops-lab-combo/cgroup.procs
```

Дальше те же проверки, что в блоке A (`hostname`, `ip link`, `ps aux`): изоляция **и** лимит памяти действуют на эту сессию.

Выход и уборка: после `exit` из оболочки `unshare` процессов в `devops-lab-combo` не остаётся - удалите пустую группу:

```bash
exit
sudo rmdir /sys/fs/cgroup/devops-lab-combo
```

Если `rmdir` сообщает «Device or resource busy», посмотрите `cat /sys/fs/cgroup/devops-lab-combo/cgroup.procs` и завершите оставшиеся PID или перенесите их в корневую группу: `echo PID | sudo tee /sys/fs/cgroup/cgroup.procs`.

### 6.5. (Опционально) Отдельный корень файловой системы - `chroot`

Чтобы получить **другой `/`** без образа Docker, нужен заранее распакованный **rootfs** (минимальный дистрибутив) и, как правило, комбинация **mount** + **pid** + **user** namespace; в продакшене вместо голого `chroot` используют **pivot_root** и overlay - так делает OCI runtime. Для курса достаточно понимать: **mnt** namespace + подготовленный rootfs - это следующий уровень сложности после сценариев выше.

### 6.6. Если прямой `mkdir` под `/sys/fs/cgroup` запрещён политикой systemd

Используйте ограниченную сессию через **systemd** и уже внутри неё выполняйте блок A (без собственного `memory.max` вручную):

```bash
sudo systemd-run --scope -p MemoryMax=200M -p CPUQuota=50% /bin/bash
```

Интерактивная оболочка может потребовать флагов вроде `--pty` в зависимости от версии systemd - при необходимости см. `man systemd-run`.

**Вывод:** вы воспроизвели вручную **часть** того, что делает OCI runtime: **namespaces** для изоляции контекста и **cgroups** для лимитов. Docker добавляет **образы, слои, сеть по умолчанию, API**
